```

reservation_id=10002  delta=+5   reason=ADMIN_APPEAL   balance=95
reservation_id=10002  delta=+10  reason=ADMIN_RESTORE  balance=65
```

## 6. 200 并发抢同一座位（表 5 W4 验收）

方式：Java 单进程 200 线程 + `CountDownLatch` 同时发起 `POST /api/v1/reservations`，
抢同一座位同一时段（B03 / 2026-11-14 16:00），测试前该用户活动预约为 0。

| 指标 | 结果 |
|---|---|
| 请求总数 | 200 |
| HTTP 201 | **1** |
| HTTP 409 `SEAT_TAKEN` | **199** |
| 总耗时 | 1003 ms |

结论：**1 成功、199 冲突**，与手册表 5 W4 的验收标准一致，冲突由数据库唯一索引裁决。

补充观察（重要）：若该用户测试前已有 1 条活动预约，先触发的是"同时最多 2 个"的业务校验，
结果会变成 `1×201 + 2×409 + 197×422 LIMIT_EXCEEDED`——**这是业务上限先于唯一索引拦截**，
不是并发缺陷。压测脚本必须先把被测账号的活动预约清零，否则会误判。

## 7. 性能基线（W7，本机）

方式：Java `HttpClient`，先预热 20 次再采样；本机回环、单机 MySQL、演示数据量（8 座位 / 7 时段）。

**单客户端顺序 300 次**

| 接口 | p50 | p95 | p99 | max | 错误 |
|---|---|---|---|---|---|
| `/api/v1/seats?room=第二阅览室` | 4.9 ms | **6.4 ms** | 7.9 ms | 14.8 ms | 0 |
| `/api/v1/slots?date=2026-11-14` | 4.2 ms | 5.8 ms | 6.3 ms | 8.0 ms | 0 |
| `/api/v1/reservations?page=1&size=20` | 4.2 ms | 6.0 ms | 6.9 ms | 7.6 ms | 0 |

**20 并发 × 25 次（共 500 请求）**

```
/api/v1/seats  rps=866  p50=17.0ms  p95=44.3ms  p99=58.2ms  max=148.6ms  errors=0
```

结论：本机基线远低于手册表 8 W7 的 **p95 < 300 ms** 要求（顺序 6.4 ms、20 并发 44.3 ms）。

限制：这是本机回环数据，**不能替代四机部署下的压测**。W7 仍需在 A 机接 C 机客户端的真实链路上，
用成员 8 的 JMeter 脚本复测；届时关注连接池 `DB_POOL_MAX` 与数据量增长后的索引表现。

## 8. 数据正确性抽查

- 通知正文以 UTF-8 存储：`HEX(LEFT(content,2))` = `E9A284E7BAA6`（"预约"）。
- 时间字段带 `+08:00` 偏移，与契约示例一致。
- 违约唯一键生效：同一预约同一 `reason` 只有一条 `credit_log`。
