# 成员4数据层交接

服务接口包：`cn.edu.stu.seatkeeper.service`，实现位于 `service.impl`；MyBatis接口位于 `mapper`，持久化对象位于 `model.po`（后缀PO），枚举位于 `model.enums`，异常位于 `exception`。所有组件由 Spring 注入，使用 MyBatis XML 和 Spring 事务。调用方不得自行 new 组件或绕过组件直接修改信用余额。此交付提供持久化原语；用户认证、角色权限、完整预约状态机、签到截止计算、扣分规则和限制判定由成员3实现。

## 调用接口

| Spring Bean | 方法 | 语义 |
|---|---|---|
| CatalogDataService | `findUser(long id)` | 返回公开用户资料或 null，不含密码哈希 |
| CatalogDataService | `listSeats(String room, Integer floor)` / `listSeats(SeatQueryDTO query)` | 两个过滤可传 null，按房间/楼层/座位号排序；DTO位于model.dto |
| CatalogDataService | `listSlots(LocalDateTime from, LocalDateTime until)` | 开始时间在 `[from,until)` 内的固定时段，正序 |
| ReservationDataService | `create(long userId,long seatId,LocalDateTime slotStart,LocalDateTime checkInDeadline)` | INSERT SELECT 从 slot 取得 slot_end，返回新预约；默认 RESERVED/version0 |
| ReservationDataService | `find(long id)` | 返回预约快照或 null；仅供受信任服务调用，API 必须自行核验当前用户 |
| ReservationDataService | `listByUser(long userId,int offset,int limit)` | 用户历史预约，时段和 id 倒序 |
| ReservationDataService | `changeStatus(long id,long userId,int expectedVersion,ReservationStatus status)` | 条件更新并递增 version；返回 1 成功、0 表示无记录/归属不符/旧版本 |
| CreditDataService | `find(long userId)` | 返回信用快照或 null |
| CreditDataService | `applyDelta(long userId,long reservationId,int delta,String reason)` | 核验预约归属，锁信用行，幂等更新余额和流水；返回 CreditLogPO |
| CreditDataService | `updateRestriction(long userId,int expectedVersion,LocalDateTime restrictedUntil)` | 修改限制截止时间并递增 version；截止可为 null，旧版本返回 0 |
| NotificationDataService | `send(long userId,String type,String content)` | 先锁该用户信用行，再插入通知并返回含 id 的快照；锁保持到最外层事务提交 |
| NotificationDataService | `page(long userId,int offset,int limit)` | 指定用户历史消息，id 倒序；offset 从 0 开始 |
| NotificationDataService | `after(long userId,long afterId,int limit)` | 指定用户严格大于游标的消息，id 正序；首次传 0 |
| NotificationDataService | `markRead(long userId,List<Long> ids)` | 只修改该用户未读消息；空列表返回 0；返回实际由未读变为已读的行数 |
| NotificationDataService | `cleanupReadBefore(LocalDateTime cutoff,int limit)` | 内部清理任务使用；只删已读且严格早于 cutoff 的有限批次 |

分页/批量大小限制为 1..1000，offset/游标非负，ID 为正数。所有持久化结果均为 model.po 中不可变 Java record；控制器应映射成VO再返回，不直接暴露PO。字段与数据字典一致。时间必须按 Asia/Shanghai 的本地时间传入，不可直接用 UTC 的 LocalDateTime。数据库精度为微秒。

`ReservationStatus` 包含 RESERVED、CHECKED_IN、CANCELLED、EXPIRED、COMPLETED。数据组件只验证枚举和版本，不替上层决定从哪个状态可以流转到哪个状态。上层应先读取状态、校验权限和状态机，再传读取到的 version；同时修改多个表时，在上层公开方法添加 `@Transactional`，组件自动加入同一事务。

信用 reason 是稳定的业务原因码，区分大小写，最长 64 字符。同一个 `(reservationId,reason)` 只能产生一条流水；同 userId/delta 重放返回原流水，delta 改变拒绝，userId 与预约归属不同拒绝。取消预约不会自动返还信用，返还需成员3按业务规则选择独立原因码和正向 delta。余额范围检查在锁内进行，失败不会夹断为 0 或 100，也不会写流水。

用户注册/认证接口没有在本模块实现。成员3创建 app_user 后需在同一事务中创建 `credit(user_id,score=100,version=0)`；通知发送也依赖这条信用行作为用户级串行化锁，缺失时以 NOT_FOUND 拒绝，不插入通知。`CatalogDataService.findUser` 不读取密码；登录需要成员3的受保护认证映射。演示 password_hash 值 `LOGIN_DISABLED_DEMO_ONLY` 不是 BCrypt 或任何可登录密码，禁止将其当默认账号口令。

注入示例：`private final ReservationDataService reservationDataService;`，构造器接收该接口，由 Spring 注入 `ReservationDataServiceImpl`。原方法名和事务语义保持不变，原 `...Record` 类型统一改为 `...PO`，旧 `service.data` 包已移除。

## 错误与并发

`DataOperationException` 为 RuntimeException，可供上层映射错误码，且会触发事务回滚：

| code | 含义 |
|---|---|
| SLOT_NOT_FOUND | 开始时间未对应已登记固定时段 |
| RESERVATION_CONFLICT | 座位或用户已占用同一活动时段 |
| NOT_FOUND | 信用操作的预约/信用账户，或通知所需信用锁行不存在 |
| OWNERSHIP_MISMATCH | 信用变动用户不属于该预约 |
| IDEMPOTENCY_MISMATCH | 已存在的幂等请求参数不一致 |
| CREDIT_OUT_OF_RANGE | 修改后余额超出 0..100 |
| VERSION_CONFLICT | 信用锁内更新未满足版本条件 |

参数错误使用 `IllegalArgumentException`/`NullPointerException`。其他外键、连接、语法等数据库异常保留 Spring DataAccessException，便于成员3统一映射并保留原始排障信息。不要把所有数据库异常都当作“预约冲突”。

预约不能使用“先查询空闲再插入”保证互斥，应直接调用 create 并处理 RESERVATION_CONFLICT。取消/过期成功提交后生成列自动变 NULL，可在相同时段重新预约。相同旧版本更新返回 0，禁止自动强行覆盖。信用统一锁定 credit 行再查当前流水，避免两个重放各扣一次；余额与流水在同一事务中提交。

Hikari 必须配置 `transaction-isolation: TRANSACTION_READ_COMMITTED`，即读已提交；外层业务事务也应保持此隔离级别，不可改回 REPEATABLE_READ。不同用户的首笔流水会查询尚不存在的幂等键，在可重复读下可能持有相互冲突的间隙锁；读已提交配合 credit 主键行锁和流水唯一键解决此竞争。集成测试直接检查 `@@transaction_isolation` 并用双事务闸门覆盖首笔并发插入。

通知 API 的 userId 必须从已认证会话取得，不能信任客户端随意传值。page/after/markRead 的 SQL 都包含 user_id。游标保存最后一条返回消息的 id，用户消息的 id 可以不连续。历史 offset 分页期间新增消息可能改变偏移；持续同步应使用 after 游标。cleanupReadBefore 只开放给内部任务，每批最多 1000，调用次数和保留期由上层调度决定。

通知按用户有序交付的条件是：所有写入都经过 Spring 注入的 send 组件，用户已有 credit 行，发送和相关业务写入使用同一个外层事务，并保持先信用、后通知的锁顺序。send 在分配自增 ID 前锁住 credit 主键行，直到最外层事务提交或回滚才释放；后一发送不会先取得更大的 ID 并提前提交，避免轮询游标永久跳过尚未提交的低 ID。不要直接使用 NotificationMapper.insert 或自行填写通知 ID。这里不锁 app_user：外层预约插入已可能持有用户外键共享锁，升级为排他锁会引入死锁。跨多个用户的外层事务应按固定用户 ID 顺序取得锁。

## 迁移与测试

默认生产目录只有 `db/migration/V1__schema.sql`，不会自动生成测试账户。demo 配置附加 `db/demo/V2__demo_data.sql`，种子默认首次执行时的次日 7 个两小时时段。演示重置可先设置会话 `@demo_date` 以固定日期；不可修改已经执行过的迁移文件来变更日期。迁移版本表必须保留。

真实 MySQL 集成测试：`seatkeeper-service/src/test/java/cn/edu/stu/seatkeeper/integration/DataIntegrityIT.java`，通过根项目 `-Pintegration verify` 执行。连接参数为 `SEATKEEPER_TEST_DB_URL`、`SEATKEEPER_TEST_DB_USER`、`SEATKEEPER_TEST_DB_PASSWORD`。默认独立实例端口33416、数据库seatkeeper_test、root空密码，仅供本机独立测试实例。测试库名称必须匹配 `^[A-Za-z][A-Za-z0-9_]*_test$`，明确拒绝 seatkeeper_test_backup、seatkeeper_testimonials、空路径、非标准/多主机/含凭据的 URL；连接参数仅接受时区、编码、SSL、超时等安全白名单，账号密码通过单独环境变量提供。

测试启动先验证 URL；每一条 DELETE 执行前，再在将执行删除的同一条 JDBC 连接上查询 `SELECT DATABASE()`，同时确认严格后缀和与配置名称完全相等。只 DELETE 七张业务表，保留 Flyway 历史。`TestDatabaseGuardTest` 是不连接数据库的普通 JUnit 测试，覆盖拒绝备份库名、不安全 URL、实际连接库名不匹配等路径，不通过尝试清理一个假数据库来测试保护逻辑。禁止对团队共享库运行集成测试。
